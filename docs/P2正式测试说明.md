# P2 正式测试说明（迁移测试：价值策略 vs 按已公布规划排序）

本文件同时是**事先登记的实验规则**：在服务器开跑前提交到仓库，跑完后不改。

## 0. 目的与边界

- **只回答一个问题**：在训练时没见过的情景里、决策信息相同的条件下，价值策略能否赶上或超过"按已公布规划排序"。这是论文 5.4 节要证明的那条故事线。
- **不加新方法，不改 `src/`**。只用 `scripts/p2_generalize.py` 已有的参数：
  - `--n-train 100`：训练情景数，20 → 100
  - `--ep-each 2`：每个情景每种行为规则的回合数，保持不变
  - `--history H`：过去 H 年变化，已有功能
- **依据**：验证试验（`results_p2_val/`，情景 201–210，规则见 `results_p2_val/PROTOCOL.md`）显示，情景从 20 个加到 50、100 个，价值策略平均从 0.863 升到 0.871、0.877，已公布规划为 0.872。在同样的情景上多跑回合（20 个情景 × 5 回合）反而下降到 0.857。

## 1. 实验设计（事先固定）

| 阶段 | 内容 | 情景 | 种子 | 作业数 |
|---|---|---|---|---|
| 1 选 H | 100 个训练情景（101–200）× 2 回合；H = 0、1、2 各一次 | 验证情景 201–210 | 0 | 3 |
| 2 正式测试 | 同上设置，H 用阶段 1 选出的值 | 测试情景 1–10 + 主情景 | 0–4 | 5 |
| 3 汇总 | 生成 `results_p2_formal/SUMMARY.md`，并做两项自检 | — | — | — |

- **阶段 1 选 H 的规则**：取验证集平均最高的 H；与最高值相差不超过 0.002 的几个 H 中，取最小的那个（偏向简单）。
- **阶段 2 只跑一次**：结果如实报告，不再调参数，也不换情景。
- 训练（101–200）、验证（201–210）、测试（1–10）三组情景互不重叠，脚本里有断言检查。
- 对照规则（持续现状贪心、按已公布规划排序、轨迹信息贪心、滚动规划）是确定性的，只在种子 0 上计算。

## 2. 结论怎么写（事先固定的措辞）

对每个测试情景 f，计算 d_f = 价值策略 5 个种子的均值 − 已公布规划。以 10 个 d_f 的均值和 t 分布 95% 区间为准：

| 结果 | 论文措辞 |
|---|---|
| 均值 > 0，且区间不含 0 | outperforms ranking on announced plans |
| 均值 > 0，但区间含 0 | matches / is slightly above, the difference is not distinguishable from zero across scenarios |
| 均值 ≤ 0 | does not beat ranking on announced plans |

同时报告"50 次比较中高于已公布规划的次数"和"10 个情景中平均更高的个数"，作为辅助信息，不作判据。

**事先说明**：验证试验里 D 组（100 个情景，1 个种子）的区间是 [−0.013, +0.024]。情景之间的差异比种子之间的差异大，所以即使均值为正，最可能的措辞也是第二种。这是预期之内的结果，不是失败。

## 3. 用服务器还是本机

| | 本机（18 GB 内存，12 核） | 服务器（建议 ≥ 6 核、≥ 32 GB） |
|---|---|---|
| 单个作业 | 约 3.9 小时（与另外 6 个作业同时跑时实测），峰值内存约 4.3 GB | 视单核速度而定，约 2.5–4 小时 |
| 同时运行 | 最多 3 个（受内存限制） | 5 个 |
| 阶段 1 + 阶段 2 | 约 4 h + 8 h ≈ 12 小时 | 约 3–4 h + 3–4 h ≈ 6–8 小时 |
| 产出数据量 | CSV 共约 100 KB | 同左 |

数据量很小，耗时主要在计算。服务器能同时跑 5 个作业时，就用服务器；否则本机放一晚上也能完成，用法相同。

## 5. 服务器：运行

```bash
cd ~/TP-MORL
git fetch origin && git checkout v20-fqi-dev && git pull
conda activate <环境>        # 需要 numpy pandas scipy scikit-learn joblib，见 environment.yml

# (1) 冒烟测试：几分钟跑完整条流程，结果没有意义，只检查能否跑通
SMOKE=1 PY=$(which python) bash 启动实验_P2正式测试.sh

# (2) 正式运行，放到后台
nohup env PY=$(which python) bash 启动实验_P2正式测试.sh > ~/p2_formal.log 2>&1 &
tail -f ~/p2_formal.log                      # 看进度
cat results_p2_formal/STATUS.txt             # 每个作业结束都会记一行 OK/FAIL
```

常用选项：
- `NPROC=5`：同时运行的作业数。默认取 min(核数 − 1, 可用内存 GB / 5, 5)，每个作业约需 4.5 GB。
- `H_FIXED=1`：跳过阶段 1，直接用 H = 1，节省约一半时间。代价是 H 不是在验证集上选的，论文里要如实写明。
- `FORCE=1`：重跑已完成的作业。默认断点续跑：日志里已有 `done in` 的作业会跳过。
- `AUTO_PUSH=0`：不自动 commit/push。默认**每个作业一结束**就提交并推送它自己的结果（CSV、日志、STATUS），备注里带该作业各规则的 ratio 摘要；阶段 1 选出 H 后再提交一次（含选择依据与自检结果）；全部结束后提交 `results_p2_formal/` 并打标签 `p2-formal-complete-<批次>`。git 操作用 `flock` 串行化；推送以远端 SHA 等于 HEAD 为准，被拒则 rebase 重推。

**启动脚本 2026-10-10 修过两处缺陷**（冒烟测试都测不出来）：
1. `xargs -L 1` 会把行尾带空格的作业行接到下一行。作业行由 `echo "... $extra"` 生成，`extra` 为空时行尾正好有空格，于是阶段 1 的 H=1 与 H=2、阶段 2 的种子 1–4 会被拼成一条命令，`--test-fields` 遇到目录名报错退出，`set -e` 使整批在阶段 1 后中止。冒烟只有 2 个 H、2 个种子，带空格的行恰好是最后一行，后面无行可接，所以冒烟显示正常。现已在交给 xargs 前去掉行尾空白。
2. 新增的逐作业提交里，备注摘要原用 heredoc 后接 `|| true`，经 `export -f` 序列化后在子 shell 里是语法错误，已改为 `python -c`。

## 6. 运行期间注意

- **跑批期间不要往服务器检出的分支推 `src/` 或 `scripts/` 的改动**，也不要在服务器上修改启动脚本：bash 是边读边执行的，中途改脚本会出错。
- **中断后直接重新运行同一条命令**，已完成的作业会自动跳过。
- **种子 0 的作业负责算对照规则，会比其他作业多花约 10 分钟**。
- 每个作业都是单线程（`TPMORL_NJOBS=1`、`OMP_NUM_THREADS=1`），同一台机器上结果可逐位复现。

## 7. 检查与发回

跑完后看 `results_p2_formal/STATUS.txt` 里的两项自检：

1. **验证试验对照**：阶段 1 中 H = 1 的结果与 `results_p2_val/D` 比对。
   - `PASS (bit-identical)`：完全一致。
   - `PASS_TOL`：差异 ≤ 0.01，属于跨平台 ExtraTrees 的正常差异（arm64 与 x86_64、不同 scikit-learn 版本之间约差 3 × 10⁻⁴），可以接受。
   - `WARN`：检查代码版本。
2. **对照规则对照**：已公布规划的得分与 `results_p2/` 中已发表的数值比对，应为 PASS。

push 后把 commit 号发回即可。主要看 `results_p2_formal/SUMMARY.md`。阶段 1 和阶段 2 必须在同一台机器上跑完，不要把服务器结果和本机结果混在一起。
