## 第 1 条 · BUILD_YEARS 改为按单元分档 —— 已改，但差异化未真正实现

**改了什么**

- `schedule.py`：删除 `BUILD_YEARS, COOLDOWN = 3, 2`，改为三张表
  - `BUILD_YEARS_BY_MODE = {"拆除重建": 5, "综合整治": 3}`
  - `BUILD_YEARS_BY_CHANNEL = {1: 5, 2: 5, 3: 5, 5: 5}`
  - `BUILD_YEARS`（兜底标量）、`COOLDOWN`
- `RenewalSchedule.__init__`：`self.build_years` 由标量改为**长度 n 的 int16 数组**，
  由 `_build_years_array()` 解析（接受 None／标量／通道字典／长度 n 数组）
- 新增 `set_build_years(units, years)`：为"按所选动作取值"预留接口
- `step()` 里 `fin = (sigma == S3) & (clock >= self.build_years)` 天然变成逐元素比较，无需改

**一处判断：拒绝按"目标功能 == 现状功能"映射综合整治**

清单第 1 条希望 P2 的两种动作按**所选动作**取值。但当前动作空间只有"原址转换为
某功能"一种动作，没有"综合整治"这一选项；而唯一看似可用的代理信号——目标功能
等于现状功能（即本会话早前定价修补涉及的那 361 个配对）——**不能用**：原类重建
仍然是拆除重建，与综合整治（不拆除、仅整治）是两回事，那样映射会把两者混为一谈，
并把 5 年的工期错标成 3 年。

**因此四个可更新通道一律取 5 年**：分档机制已就位，但实际差异为零。两个前置条件
（清单第 8 条的数据字段、或动作空间引入综合整治动作）任一到位，改一张表即可。
源码里已写明这一限制与不可用的代理映射。

**连带已改**：`env_gym.py` 的 `F[:, 12]`。原先一律 `clock / TAU_EXT`，既漏掉 S1
的有效期倒计时，也会在建设年限取 5 后给出 >1 的特征值。改为"当前状态内的进度"：
S1 用 `tau / tau_max`，其余状态用 `clock / max_clock()`，其中 S3 的上限是**该单元
的** `build_years`。实测 15 年逐年最大值落在 [0.000, 1.000]，越界年数 0。

## 第 3 条 · 后半程退化检查 —— 已诊断，选路线 (c)

新增 `scripts/diag_horizon.py`：只模拟制度状态机（不需要用地图与奖励），对每个
立项年份估计期内建成概率。**不依赖策略**，故结论对任何策略都成立。

| 立项年 | 期内建成概率（建设 3 年） | 期内建成概率（建设 5 年） |
|---|---|---|
| 1 | 0.891 | 0.812 |
| 5 | 0.710 | 0.710 |
| 8 | 0.643 | 0.338 |
| 9 | 0.502 | 0.173 |
| 10 | 0.339 | **0.000** |
| 11 | 0.174 | 0.000 |
| 12–15 | **0.000** | 0.000 |

**确认存在退化**：不可交付的年份由 4/15（27%）扩大到 6/15（40%）。

且退化比 `Floor` 一项更深：空间目标只在建成年（S4）改写用地图，所以第 10–15 年
立项的单元，**11 个目标里只有三个惩罚项（Cost / Disrupt / Expire）会响应**。这些
年份任何动作都严格为负，最优行为必然是"到此为止"。所以策略不会退化成乱动——它会
正确地学会停手；但这 40% 的规划期没有决策内容。

**三条路线的选择：取 (c)，明确保留为设计特征。**

- 路线 (a) 延长 T：只能稀释，不能消除。死尾长度恒等于 `build_years + 1` 年，与 T
  无关——实测 T=20 时仍是 6 年（30%）。已提供 `--horizon` 供敏感性分析
- 路线 (b) 部分交付信用：**主动否决**。`Floor` 与七项空间目标共用同一个建成事件，
  只给 `Floor` 部分信用而用地图不动，恰好重新制造出本会话早前诊断并修掉的那个
  病症（白拿建面、用地图不变、成本不计）。要正确实现，得让用地图也按施工进度
  渐变，那是一次结构性改动，不在本轮
- 路线 (c) 保留：它对应现实中"末期立项确实无法在本轮规划期见效"，是真实的时间窗
  硬约束，也让"何时动"的分量变重——这正是本项目的主张所在

**论文须写明**：`Floor` 的有效决策窗口是前 9 年，后 6 年为不可交付区。

## 第 5 条 · 现行法定窗口情景对照 —— 已加

新增 CLI `--tau-valid --tau-ext`。基线仍用实测标定（3+2），对照组
`--tau-valid 2 --tau-ext 1` 即深规划资源规〔2019〕4 号第三十二条的法定上限 3 年。

**一处必须同时改的地方**：目标归一化的分母是"当前约束情景下参考策略集的可达
上界"，制度窗口一改，可达上界随之改变。若分母缓存键里不含制度参数，对照情景会
**静默复用基线情景的分母**，两组结果不可比。故 `scale.py` 的 `_tag()` 现在追加
制度标识：

```
B900_C3_G0_V3E2D2Y1-52-53-55-5     基线（有效期 3+2，冷却 2，各通道建设 5 年）
B900_C3_G0_V2E1D2Y1-52-53-55-5     法定窗口对照
B900_C3_G0_V3E2D0Y1-52-53-55-5     冷却期 0 档
```

**这也意味着修补前的全部分母缓存都要删掉**（键值格式已变，旧文件不会被命中，
但会白占空间且容易误读）。

**另一处易踩的坑（已修）**：`RenewalSchedule.__init__` 原来把
`tau_max=TAU_VALID + TAU_EXT` 写在**函数签名的默认值**里。默认值在函数定义时就
已求值，而本项目情景参数的既有做法是由 CLI 事后改写模块常量——那样改法对 `tau_max`
完全无效，法定窗口对照会跑出与基线一模一样的结果，且**不报错**。现在四个默认值
（quota / tau_max / build_years / cooldown / hazard）一律在 `__init__` 体内解析。

**新增 `src/tpmorl/rl/scenario.py`**：情景参数的改写与命名集中一处。原先只有 3 个
预算类参数、在 `train_ppo.py` 与 `exp_opt_quality.py` 里各抄一遍（后者因为用 spawn
起子进程，子进程会重新 import 拿回默认值，所以两处 worker 里还各抄一遍，共 3 处）。
现在多了 4 个制度参数，抄写式改写必漏，故改为 `scenario.apply()` 统一调用。

## 第 6 条 · 标定样本的制度期说明 —— 已补

`schedule.py` docstring 的 `TAU_EXT` 条目下补入完整说明：标定用的 109 对配对来自
2010–2018 年，当期适用深规土告〔2010〕16 号，并无两年有效期之设；深建规〔2025〕
4 号要求各区对"公告未明确有效期"的存量计划补设有效期，正是旧计划原本没有有效期
的直接证据；而第三十二条第一句即限定"本规定施行后批准的"更新单元计划。**结论：
实测中位 3 年不是"条文与现实脱节"，而是旧制度下本无此限，两者不冲突。**
