## 一、状态机：显式的剩余时间

`RenewalSchedule` 新增三个方法，全部是**纯读**——不改任何转移，可在 `obs()` 里
任意调用：

- `remaining_valid()`：S1（待批）单元的剩余有效年数
- `remaining_build()`：S2/S3（已批/在建）单元的剩余建设年数
- `expected_years_to_delivery(if_initiated_now=False)`：期望还需几年交付

### 两个设计决定，及其理由

**1. 期望离开 S1 的年数用反向递推，不用"次年获批"的乐观假设。**

`_exp_leave[k]` 定义为：已在第 k 个有效年、期望再过几年离开 S1（获批**或**失效
都算离开）。按 `HAZARD` 逐年条件批准率反向递推。

为什么不用乐观口径：本项目要诊断的恰恰是"立项晚于可交付窗口"这一行为。若把
期望交付年数按"明年就批"来算，模型会系统性高估可交付性，于是它自己就会做出
窗外立项——我们要观测的病因被写进了观测本身。默认档下 `E[离开S1] = 3.33` 年。

**2. 剩余建设年数写成一般表达式，而不是当前那个常数。**

当前的时钟推进规则使该式恒等于一个常数，但规则一改（例如把计时移到完工判定
之前）常数就错而表达式仍对。这里刻意不做常量折叠。

### 验证方式：逐步模拟，不靠读代码

差一年是这类代码最常见的错，读代码读不出来。做法是：强制审批通过，把单元推过
整条管道，每一步都把**预测的剩余年数**与**把状态复制一份往前放、实测到完工的
步数**对比。

- 建设年限 3 / 5 / 7 三档，每档在每个状态、每个时钟值上：预测与实测**逐位一致**
- 零批准率下 `remaining_valid()` 序列长度等于 `tau_max`、末值为 1

## 二、观测：逐单元 slack

`N_FEAT` 由 16 增至 22，新增 6 维（下标 16..21）：剩余有效年 / 剩余建设年 /
期望交付年数 / slack / 期内可交付标志 / 在建管道占比（后者为全局、随时间变化）。

**为什么这些不是已有特征的重述**：原第 12 维进度特征报告的是**已过**时间而非
剩余时间；原第 14 维时间特征是全局的，无法区分建设年限不同的单元。

**slack 的口径**：以决策期 T 为界，按"若本年立项"评估，不可达单元钳到下界。

**刻意未加的两个特征，理由**：年度配额与偏好权重向量在逐 α 训练的单次运行内
恒定，作为特征不含任何信息。

**顺带修掉的一处不一致**：`pairs()` 末行（STOP 行）的时间进度项此前未钳到 1，
与 `obs()` 里的钳制口径不同。这是旧有遗漏，非本轮引入。

## 三、资金：承诺预算与可用预算分离

新增 `BUDGET_MODE`：

- `upfront`（默认）：立项当年全额支付，Cost 按完工年计入 —— 与既往结果逐位等价
- `staged`：立项当年付 `STAGE_INIT=0.2` 前期款，余额在实施期内按年等额支付，
  **且 Cost 目标改按实际支付年计入**

### 一个关键的设计简化及其正当性

可用预算的语义统一为"已拨付、未承诺"。立项那一刻即锁定该单元的**全额**成本，
因此后续的按年支付不可能失败——单一的硬负担能力掩码就够了，掩码里无需再做
跨年现金流可行性检验。

### 按年支付的时点与"施工扰动"目标同一判据

按年支付挂在与施工扰动目标**同一个**在建判定上。这是刻意的：两者若各自判断
"哪些单元今年在建"，迟早会差一年，而这类不一致本项目已经记录过一次
（见 `docs/跨期结转_口径修正_v1.md`）。同时，单元有效期届满时释放其未付承诺，
并在 step 内断言承诺总额非负且与逐单元未付台账相符。

### 验证

| 检验 | 结果 |
|---|---|
| `upfront` 下随机基线轨迹与改动前 | **逐位相同**（4252 字节全等） |
| `staged` 下 Cost 总额 vs 支付总额 | **10982.0 逐位相等**（`scripts/verify_budget_identity.py`，种子 7） |
| 期末未付承诺 | 0（全部结清） |
| 可用预算是否为负 | 从未 |
| 台账断言 | 全过 |

对照方式：用 `git archive` 取出改动前版本的包，与新版跑同一随机种子逐步对比。
选随机基线是因为它不读观测，因此不受特征位宽变化影响——这是唯一能做逐位对照的
策略族。

### 附带暴露的旧口径不自洽（值得写进论文方法节）

> **更正声明**：本节此前引用的一组金额（4290 / 9180 / 13470，以及 staged 下的
> 12016.0）未随文记录种子与动作策略，交叉检查方扫遍 5 个种子 × 两种资金口径 ×
> 三档评价期均复现不出，故**那组数字作废**。结论（口径不自恰的机理）不变，但数字
> 一律改为以下可复现值。

固定复现口径：`PYTHONPATH=src python3 scripts/verify_budget_identity.py`
（种子 7、随机可付性策略、决策期 15、预算 900、结转 3、增长 0）。该脚本把三条
恒等式写成硬校验，不成立即非零退出，可直接当回归测试用。

`upfront` 下预算实际支出 **13480.0**，而 Cost 目标只记 **8580.0**。差额 **4900.0**
逐位等于未完工单元的成本（后者由状态机直接算出，不是把差额倒过来定义的）：

```
完工单元成本 8580.0  +  未完工单元成本 4900.0  =  承诺总额 13480.0   （占承诺 36%）
实付现金 13480.0     ==  承诺总额 13480.0                            （立项即全额扣款）
```

即失效单元花掉了预算、却从不进入 Cost 目标——模型看不到"沉没成本"。

`staged` 下同一策略的实付现金 **10982.0** 与 |Cost| **10982.0** 逐位相等，期末未付
承诺为 0：按进度付款使现金流与成本口径合一。注意 staged 的承诺总额（15350.0）大于
实付现金，差额是未完工单元被作废时**释放**掉的剩余义务，不是被支付掉的——这正是
两种口径的实质差别。
`staged` 口径下两者按构造相等，这一不自洽消失。

## 四、场景参数扩展

新增五个 CLI 参数：`--quota`、`--tau-approval`、`--build-years-by-channel`、
`--budget-mode`、`--stage-init`。

`--tau-approval` 的**口径必须在论文里写明**：它把逐年条件批准率整体替换为常数
风险率 1/τ_A（几何近似）。默认档 `HAZARD` 是由累计获批数逐年反解的实测向量，
本参数是它的**敏感性对照**，不是更精确的估计。

`--build-years-by-channel` 的**口径同样必须写明**：单元表没有更新方式字段，
无法逐单元判定拆除重建／综合整治，故一切通道分档年限只能作**情景参数**报告，
不得写成实证标定值。这也正是四个通道此前一律取 5 年的原因。

### 全部进缓存键，但只在非出厂值时进

配额、批准率、资金口径三者都改变可达上界（分母的定义就是可达上界），漏入键会
让对照组静默复用基线分母——与此前定位的 `FAR_GROWTH` 泄漏是同一类缺陷。
但只在**非出厂值**时入键，以保证默认档的既有缓存逐字有效。

| 情景 | `inst_tag()` |
|---|---|
| 默认（与改动前逐字相同） | `V3E2DAY1-52-53-55-5T15X26` |
| 配额 6 | `…T15X26Q6` |
| τ_A=3 / τ_A=5 | `…T15X26A3` / `…T15X26A5` |
| staged / staged 且前期款 0.3 | `…T15X26MS02` / `…T15X26MS03` |
| 通道 2 改 3 年 | `V3E2DAY1-52-33-55-5T15X26` |
| 全档 3 年 | `V3E2DAY1-32-33-35-3T15X24`（T_eval 随之由 26 变 24） |

### 验证

- 改动前 / 改动后的默认档、γ=0.90 档、T=20 档，三种情形的键**逐字相同**
- 五个新参数各自产生互不相同的键，无一漏入
- `reset()` 后五项全部复原到出厂值（逐项比对相等）
- 五类非法输入全部拦住：未知通道、τ_A≤0、非法资金口径、前期款越界、
  分档格式错误

### 键集为什么改成签名反解

F-11 手工补键后**我自己又漏了一个**：`obs_lifecycle`。消融组靠它区别于主组，
漏掉就等于拿主组的观测维度去重放消融组的权重，于是审计把 25 个 run 全判"未匹配"
——这份工具的职责恰恰是判定"落盘值能否复现"，漏键会把自己的错读成动力学污染，
是最难发现的一类。手列键集一定会再漂，故改为

```python
_EXPLICIT = {"budget", "carry", "growth", "horizon", "horizon_eval", "gamma"}
_INST_KEYS = tuple(k for k in inspect.signature(scenario.apply).parameters
                   if k not in _EXPLICIT)
```

这让"以后 `apply` 新增参数而此处忘记同步"在结构上不可能发生。反解结果实测为
10 个键：`tau_valid, tau_ext, cooldown, build_years, quota, tau_approval,
build_years_by_channel, budget_mode, stage_init, obs_lifecycle`。

## 资金分解闭合式的缺项（闭合校验抓到的真实缺陷）

F-04 把"零立项也计资金分解"打开后，`staged` 一组的闭合校验不通过。查清后是
**分解式本身缺一项**，不是误报。可用预算的逐年递推是

    b_{t+1} = min(b_t − 承诺_t + 释放_t + B, carry_cap·B)

记 `clip_t` 为当年超上限被作废的额度，则 `b_{t+1} = b_t − 承诺_t + 释放_t + B − clip_t`。
从 `b_0 = B` 望远镜求和到 `t = T−1`（名义到账共 `B·(T+1)`）得

    Σ承诺 − Σ释放 + Σclip + b_T == B·(T+1)

**释放项**（有效期届满被撤的单元，其剩余未付承诺退回可承诺额度）此前不在分解式
里。`upfront` 口径下立项即全额付清、无未付承诺，释放恒为 0，所以那 15 组一直闭合；
`staged` 组实测分解和 1.2095 而应为 1.0667，差额 0.1428 恰是释放额占比。

修法：`env_gym` 逐年记 `released`，`metrics.funds_decomposition` 增列
`released_ratio` 并计入恒等式。rec 缺该列时按 0 处理——v15 之前的批次全是
`upfront`，按 0 即正确。

**数值中性已验**：`main` 组（upfront）改动前后 `objectives.csv`、`curves.csv`
**逐字节相同**，逐年记录只多出 `released` 一列且该列全为 0，其余列逐位相同。
